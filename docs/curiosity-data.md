# Curiosity (MSL) rover traverse and science targets

Static GeoJSON layers generated from NASA public data. This document records what they are, where they came from, and how they were validated. Nothing here is invented: every number below comes from the source files listed in References, and every failure mode is listed with the affected rows.

Generated by `scripts/curiosity-convert.mjs` (Node ≥ 18, no dependencies). Re-run it from the repo root to regenerate everything in this section.

## What the data is

**Traverse** — `localized_pos.csv` (PLACES bundle, `urn:nasa:pds:msl_places:data_localizations:localized_pos.csv`, version 42.0, file created 2026-04-30, content covering 2012-08-06 → 2026-04-17). It lists every localized rover position. The file contains `SITE` rows (site-frame origins) and `ROVER` rows; we keep **ROVER rows only** because SITE rows duplicate the same positions. Rows are sorted chronologically by `sol`, `sclk`, then RMC (`site/drive/pose`). 1,349 stops, sol 0–4865.

**Targets** — the MSL science targets table from the PDS Analyst's Notebook, exported via the Target Summary page (Mission tab → science targets → File → Export as CSV). File name from the export: `2026-0912-MSL-Science-targets.csv` (Notebook build 2026-0912), retrieved 2026-11-14. 10,258 rows, sol 1–4843, 10,216 unique target names (some names, e.g. `LD RMI control`, are intentionally reused on multiple sols and are kept as separate rows). The Notebook UI counter showed 10,257 — the one-row difference between the UI counter and the CSV export is reported, not reconciled (no scraping was used to reconcile it).

**Samples** — Curiosity's **drill-sample sites** — the "small rocks the rover picked, with infos and (in the Notebook) pictures" — appear inside the targets table: every row recorded at a drilling campaign's RMC is a target observation associated with that sample (approach, mini-drill, full drill, tailings, sieve, CheMin/SAM handoff). `curiosity_samples.geojson` is a **curated one-Point-per-drilling-campaign** layer, derived only from the committed targets CSV; nothing is invented and no new data sources were used. 39 campaigns, sol 152 → 4802 (Yellowknife Bay John Klein through the boxwork-era campaigns):

- 37 with position (coordinates = per-campaign mean of located rows at the RMC; rows within one campaign agree to sub-meter), elevations climb from −4,521 m (Yellowknife Bay) to −3,611 m (boxwork region).
- 2 campaigns have **NULL** easting/northing in the source export → `geometry: null`: `Abanay / Nevado_Sajama` (site 120, drive 82) and `Nevado_Sajama2` (site 120, drive 574). Both are in the current drill sequence (sols ~4713–4802); NASA has not localized them publicly yet in this export.
- 4 boxwork-era campaigns have no `drill_hole` rows and are **inferred from tailings rows** in the export (`Altadena` sol 4566, `Valle_de_la_Luna` sol ~4693, `Abanay / Nevado_Sajama` sol ~4730, `Nevado_Sajama2` sol 4802); they are flagged `inferred_from_tailings: true` in the GeoJSON.

Properties: `sample`, `nearby_targets` (every AN target name at the RMC, unfiltered — e.g. `John_Klein` campaign's 36 pointings), `n_nearby_targets`, `sol_range` (spans **all** rows at the RMC — pointings + drilling — it brackets drill sol, it does not pin it: e.g. Windjana sol_range 611–676, hole drilled at sol 622 per the `Windjana_drill_Hole` rows), `rmc`, `locator` (image product id of an image at the site; the pictures themselves live in the Notebook — fetch on demand; **no pixel data is committed**), `inferred_from_tailings`.

**Pictures of the samples are intentionally not in the repo.** Sub-meter, full-res Mastcam imagery of the selected rocks sits behind the Notebook's per-target pages and the PDS Imaging Node. Committing it would mean bulk-downloading thousands of images (effectively scraping); the GeoJSON/Locator carries enough to fetch any of it on demand via the public AN/PDS services if the app needs it later.

## CRS and conversion

The source files use global **northing/easting in meters** in the ORBITAL(0) equirectangular frame. The PLACES SIS §4.4.2.4 defines, with Re = 3,396,190 m (equatorial radius) and Rs = 3,376,200 m:

```
lon                      = easting  / Re * 180/pi      (east-positive)
lat_planetocentric       = northing / Re * 180/pi
lat_planetodetic         = atan( tan(lat_pc) * (Re/Rs)^2 )
```

These formulas were verified numerically against the CSV itself (they reproduce all rows exactly).

**Geometry coordinates are `[lon, lat_planetocentric, elevation]`** because the project's HiRISE basemap (NASA Trek `curiosity_hirise_mosaic` ImageServer) reports `spatialReference` wkid **104905** — IAU 2015 Mars ocentric (planetocentric latitude). Confirmed 2026-11-14 from the service metadata (`?f=json`). The planetodetic latitude is kept in each feature's properties (`lat_planetodetic_deg`).

Beware the trap: treating the two latitude flavors as interchangeable shifts points by **~3.2 km north–south at Gale** (lat −4.6°). This is the PLAN.md spike-#4 failure mode. If the viewer ever renders these files with Cesium `GeoJsonDataSource`, Cesium's `Ellipsoid.MARS` treats Cartographic latitude as geodetic — consistent with an *ographic* basemap; consistent, if the basemap is ocentric too. Mixing conventions is the bug, not either convention alone.

Elevations are meters relative to the **Mars areoid datum** (cartographic convention, positive up), not the 3,396.19 km reference ellipsoid — see PLACES SIS §3.9.3 for the areoid treatment and §4.4.2.4 for the definition of `elevation`.

Coordinates are rounded to 7 decimals (~1 cm), elevation to 1 m. Values recoverable to full precision from the committed raw CSVs.

## Processing steps (`scripts/curiosity-convert.mjs`)

1. Parse both CSVs (RFC-4180-ish, handles quoted fields).
2. Traverse: filter `frame == "ROVER"` and `sol >= 0`; map easting/northing to degrees per the formulas above; sort; emit a `LineString` (first feature) plus one `Point` per stop.
3. Targets: keep every row; if `Easting_m` or `Northing_m` is `NULL`, the feature gets **`geometry: null`** and `null` coordinates (RFC 7946 permits null geometries).
4. Samples: curate 39 drilling campaigns by `(site, drive)` RMC from the targets rows (explicit list in the script); assert each campaign matches ≥ 1 row; coordinates = per-campaign mean of located rows (sub-meter spread); `sol_range` spans all rows at the RMC; four boxwork-era campaigns inferred from tailings rows (flagged); two NULL-position campaigns → `geometry: null`.
5. Post-write structural validation re-reads all three files: FeatureCollection type, finite coordinates, lon ∈ [−180, 180], lat ∈ [−90, 90], elevation finite, LineString ≥ 2 positions. Exit code 1 on any violation.

| **Registration vs HiRISE mosaic** | **Not pixel-measured — see below** |

**Registration.** PLACES documents its localized positions as accurate to **~0.5 m** against the orbital base map (SIS §4.4.1.2), and both our geometry and the project's HiRISE mosaic use the same ocentric convention, so no systematic CRS offset exists. An *independent pixel-level* offset was **not** measured: the only imagery export available publicly in-session is Trek's `exportImage` (0.25 m/px), and at the Gale site there is no isolated, unambiguous rover-track landmark I could lock onto from a desktop without local vision of wheel-track width. What was verified instead: (a) identical CRS family (EPSG:104905 ocentric) on both sides; (b) bboxes well inside the mosaic; (c) first stop lands on the published Bradbury Landing coordinate; (d) target rows that share an RMC land on identical coordinates. For a pixel check later: `exportImage?bbox=…&bboxSR=104905&imageSR=104905` around any traversed waypoint with visible wheel tracks, overlay the LineString, measure the residual — if it is within ~1 px (0.25 m), registration is confirmed; if it shows a consistent ~3.2 km lat shift, the basemap CRS handling is wrong.

**Size note.** The targets GeoJSON (3.8 MB) could be slimmed (properties carry the full meters tuple for traceability). If load time matters, split by quadrant or drop `easting_m`/`northing_m`/`lat_planetocentric_deg` from properties — none of this changes the geometry.

## What was deliberately not done

- No website/viewer code was touched (data + provenance only).
- No scraping / no bulk image download: the Notebook's public UI export was used for the targets CSV; the PDS bundle was used for the traverse; sample pictures and per-target detail stay in the Notebook/PDS — the `locator` field is the hook to fetch them on demand.
- The 1.16 GB `msl_orbital_map.img` / 296 MB DEM were **not** downloaded; only the map XML label (16 KB) was fetched for projection parameters.
- Raw files committed because all are < 5 MB.
